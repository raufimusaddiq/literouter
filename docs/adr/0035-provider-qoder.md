# ADR-0035: Qoder executor and catalog

- Status: Accepted
- Date: 2026-11-23
- Origin: recovered from code comments in the 2026-11-23 comment audit

## Context

Qoder is a non-OpenAI-compatible upstream. The router impersonates `qodercli`: requests are COSY-signed (RSA + AES + MD5), bodies are obfuscated to pass Alibaba Cloud WAF, responses arrive in a `{statusCodeValue, body}` SSE envelope, and tokens come in three kinds (device `dt-`, job `jt-`, PAT `pt-`). Protocol pieces were ported from CLIProxyAPIPlus (qoder-provider branch) and qoder2api. Because it is a binary-ish, signed upstream, everything is handled inside the executor under `open-sse/executors/qoder.js` and `open-sse/shared/qoder/`.

## Decisions

### D1. Exact server-published model_config or a hard error

Qoder silently downgrades to a different model when the wrong `model_config` is sent, so the per-model config is fetched live from `/algo/api/v2/model/list` (not a static map) and a missing entry is a hard error ("model config not yet fetched, retry shortly"). Model keys are canonical (auto, ultimate, performance, efficient, lite, plus frontier `*model` ids); the translator feeds `qoder/<key>` and the prefix is stripped. Hidden (`enable:false`) models stay routable and are still cached.

**Where:** `open-sse/executors/qoder.js`: `QoderExecutor`; `open-sse/services/qoderModels.js`

### D2. Token types and hosts

Device tokens (`dt-`) use `api3.qoder.sh`. Job tokens (`jt-`) must use `api2.qoder.sh` because api3 rejects them with 403 "Login expired", as the official qodercli does. PATs (`pt-`) cannot sign COSY requests; they are exchanged through a plain, unsigned JSON POST for a short-lived job token and the userId is resolved, so signing and catalog fetch work (device and job tokens skip this). The same PAT exchange is required in usage lookups, and PAT connections keep the token in `apiKey`, which the `/v1/models` Qoder resolver must pass on or the live catalog silently fails and falls back to the static list. Device tokens do not refresh through OAuth (the upstream returns 403 for our flow), so failure surfaces as 401 on chat and the dashboard tells users to re-login (tokens last about 30 days); the connection test probes the userinfo endpoint with the device token with `refreshable: false` and no expiry check so revoked tokens surface. A failed refresh/auth error is mapped to 401 so chatCore prompts re-auth instead of returning 500. The device flow prefers the PKCE verifier generated by Qoder's own `requestDeviceCode`, and polling treats 202/404 as pending and 200 as done.

**Where:** `open-sse/shared/qoder/constants.js`; `open-sse/executors/qoder.js`; `open-sse/services/usage.js`; `src/lib/oauth/services/qoder.js`; `src/app/api/oauth/[provider]/[action]/route.js`; `src/app/api/providers/[id]/test/testUtils.js`

### D3. Signing and encoding are part of the wire contract

`execute` is overridden entirely: the body is built from the translated payload, encoded with `QoderEncodeBody` (base64, reorder thirds as tail/mid/head, custom alphabet; sent with `&Encode=1`) before signing, and COSY headers are computed from the encoded body bytes. COSY uses an AES-128-CBC payload with the key wrapped in RSA, an MD5 signature over `payload || cosyKey || timestamp || body || sigPath`, and about 17 `Cosy-*` / `X-*` headers whose casing must match qodercli (`Cosy-Machineid`). The upstream validates header constants against the values used at signing time. The AES key is the first 16 characters of a fresh UUID string (hyphens included), fresh per request. `Accept-Encoding` is forced to identity because gzip triggers signature validation on Qoder's CDN. A failed proxied request may already have reached Qoder, and replaying the same signature directly reuses its requestId and returns 403 code 103, so the caller must retry through `execute()` with fresh signing.

**Where:** `open-sse/shared/qoder/cosy.js`; `open-sse/shared/qoder/encoding.js`; `open-sse/executors/qoder.js`: `execute`

### D4. Context-window tier auto-escalation

Each model_config lists `context_config` tiers (for example 200K / 400K / 1M) while `max_input_tokens` carries only the IDE's selected tier (about 180K). A qodercli-style client has no picker, so a long session would be rejected even though the model supports 1M. The router estimates prompt size (CJK about 1 token per character, others about 4 chars per token, because chars/4 underestimates CJK by up to 4x), picks the smallest advertised tier that fits with headroom and never below the default, and mirrors the choice into `parameters.context_length`, `chat_context.extra.ideModelConfigOverride.max_input_tokens` and `model_config.max_input_tokens`. `QODER_CONTEXT_TIER` overrides with auto (default), max, default, or a tier name such as `1M`. The functions are pure.

**Where:** `open-sse/shared/qoder/contextTier.js`; `open-sse/executors/qoder.js`; `tests/unit/qoder-context-tier.test.js`

### D5. Attachments are uploaded, not inlined

Native qodercli uploads images and PDFs via a COSY-signed multipart PUT to `/algo/api/v2/image/upload` (field `file`) and sends the returned OSS URL. Forwarding data URIs made 10 MB images into 30 MB+ JSON and upstream 413s even though the model window is about 200k tokens. Inlined images are uploaded (cached by sha256), huge non-image file blocks become short stubs, and leftover data URIs are capped. Claude-style `{type:"image", source}` blocks are converted to OpenAI `image_url`. System messages are hoisted out of the messages array (Qoder rejects them there); other multipart content is flattened to text, except images. The legacy `image_urls` / `chat_context.imageUrls` slots stay null, as in qodercli. Image refs are included in the chat record id hash so the same prompt with another image gets a distinct `chat_record_id`.

**Where:** `open-sse/shared/qoder/attachments.js`; `open-sse/executors/qoder.js`: message normalization and `buildQoderRequestBody`

### D6. Unwrap the SSE envelope carefully

Each upstream line is `data: {"statusCodeValue":200,"body":"<json>"}`; the inner chunk is re-emitted as plain OpenAI SSE. The first frame is peeked for errors before committing to HTTP 200, preserving upstream statuses so chatCore can lock and fall back; the peeked bytes are returned as `consumed` so nothing is dropped. Billing signatures (code 110 daily count, 112 quota exhausted, 10605 queue throttle, or a `pricingUrl`) map to 403 for quota/account fallback, and a billing or quota envelope at any later position becomes a structured error chunk, not fake assistant text, which `parseSSEToOpenAIResponse` turns into a non-200 result (statuses 400-599 preserved, anything else 502). Qoder keeps the socket open after the terminal frame (agent keepalive), so non-streaming `response.text()` would hang; on terminal events the upstream reader is cancelled and the stream closed. The stream uses `start()` plus a loop, not `pull`, because a pull that buffers a partial line without enqueueing is never re-invoked.

**Where:** `open-sse/executors/qoder.js`; `open-sse/handlers/chatCore/sseToJsonHandler.js`

### D7. Usage frames are coalesced

Qoder puts `finish_reason` on `delta` and sends token counts on a later `choices: []` frame, but downstream OpenAI/Claude clients read usage only from the finish chunk and drop empty-choices frames. The coalescer holds empty-finish and usage-only frames and emits one include_usage-style chunk as soon as both are present (finish then usage), without waiting for `[DONE]` or keepalive. The dashboard still sees tokens because `extractUsage` runs on every forwarded frame.

**Where:** `open-sse/shared/qoder/sse.js`: `createQoderSseCoalescer`

### D8. Dashboard surfaces the canonical id and the current name

The dashboard lists models as `qoder/<key>`, the id the chat router expects. Display names follow upstream renames (the key stays stable, such as `qmodel_latest`) by upserting on refresh.

**Where:** `src/app/api/providers/[id]/models/route.js`; `src/shared/utils/providerCustomModels.js`

## Consequences

- Sending the wrong or a missing `model_config` makes Qoder silently serve a different model.
- Signing the unencoded body, mis-cased headers, or gzip responses fail signature validation or WAF checks.
- Job tokens on api3 return "Login expired"; PATs signed directly fail.
- Inlining attachments causes 413s; skipping tier escalation rejects long sessions.
- Not cancelling the reader at terminal frames hangs non-streaming clients; not coalescing usage drops token counts for clients.
- Replaying a signed request unchanged yields 403 code 103.
